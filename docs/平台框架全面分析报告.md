# CaseMind 平台框架全面分析报告

## 📊 一、整体架构概览

### 1.1 核心模块组成

```
CaseMind 平台
├── 记忆系统 (Memory)
│   ├── MemoryAgent - 增量文档索引与摘要
│   ├── VectorStore - FAISS向量检索
│   ├── HybridRetriever - BM25+向量混合检索
│   └── KP Store - 结构化知识库
│
├── 历史资产系统 (Legacy)
│   ├── LegacyCase - Excel用例解析与存储
│   ├── LegacyXMind - XMind树结构解析
│   ├── StyleProfile - 团队风格画像
│   └── InferredKP - 五阶段分析反哺候选
│
├── AI对话系统 (Query)
│   ├── QueryAgent - RAG问答
│   ├── @提及注入 - 文件内容引用
│   └── 多模式支持 - QA/Testcase/XMind/Chat
│
├── 用例生成流水线 (CaseGen)
│   ├── Slicer - 需求切分为FeaturePoint
│   ├── Generator - 并行生成用例（支持few-shot）
│   ├── Merger - 去重与集成用例补充
│   └── Validator - 字段完整性校验
│
└── 历史分析系统 (LegacyAnalyzer)
    ├── 五阶段分析流水线
    ├── 信号抽取（LLM）
    ├── 反哺候选生成
    └── 风格画像提取
```

## ✅ 二、功能实现情况分析

### 2.1 历史用例和XMind能否到达Memory面板？

#### ✅ **部分实现，但有局限性**

**当前实现路径**：

1. **五阶段分析 → 反哺候选 → Memory审核**
   ```
   历史用例/XMind 
     ↓ [POST /legacy/analyze]
   五阶段分析（聚类→信号抽取→反哺）
     ↓
   InferredKnowledgePoint（反哺候选）
     ↓ [memory/<project>/legacy/inferred/inferred_kps.json]
   Memory面板 → "反哺审核"Tab
     ↓ [人工accept/reject]
   KnowledgePoint（合入KP库）
     ↓ [knowledge_points.jsonl]
   进入memory.md和memory_prompt.txt
   ```

**关键代码位置**：
- `backend/agents/legacy_analyzer/runner.py` - 五阶段分析主流程
- `backend/services/legacy_service.py:309-348` - 反哺候选审核API
- `frontend/src/pages/Memory.jsx` - Memory面板UI（包含"反哺审核"Tab）

**问题**：
1. ❌ **需要手动触发**：必须运行五阶段分析才能产生反哺候选
2. ❌ **需要人工审核**：默认情况下需要人工accept才能合入KP库
3. ❌ **只处理隐性规则**：五阶段分析主要提取"隐性规则"，不是原始用例内容
4. ⚠️ **自动接受有风险**：虽然可以开启`enable_legacy_inference_auto_accept`，但文档明确标注"高风险"

### 2.2 能否作为AI对话时的内容参考？

#### ✅ **已实现，通过@提及机制**

**实现方式**：

1. **@提及注入到Prompt**
   ```javascript
   // frontend/src/pages/Chat.jsx
   const mentionCandidates = useMemo(() => {

       label: stripExt(it.name),

       catLabel: '历史用例'
     }));
     
     // 历史XMind池
     const xmPool = legacyXMind.map(it => ({
       label: stripExt(it.name),
       category: 'legacy_xmind',
       catLabel: '历史 XMind'
     }));
   });
   ```

2. **后端渲染为Prompt文本**
   ```python
   # backend/services/legacy_service.py:351-374
   def resolve_legacy_case_mention(project, file_id):
       """把一份历史用例 Excel 渲染为 prompt 注入文本。"""
       cases = legacy_store.load_cases(project, file_id)
       lines = [f"# 历史用例：{meta.name}"]
       for c in cases:
           lines.append(f"\n## {c.case_id}  {c.title}")
           for s in c.steps:
               lines.append(f"  {s.index}. {s.action} → {s.expected}")
       text, truncated = _truncate("\n".join(lines))  # 最多40000字符
   ```

3. **注入到QueryAgent的system prompt**
   ```python
   # backend/agents/query_agent.py:61-73
   def _format_references(blocks):
       parts = [
         "以下是用户通过 @ 引用的文件内容。"
         "生成用例 / XMind / 答案时，请结合这些内容进行分析和回答"
       ]
       for i, b in enumerate(blocks, 1):
           parts.append(f"\n--- 引用文件 {i} · @{b.get('label')} ---")
           parts.append(b.get("content"))
   ```

**工作流程**：
```
用户在对话框输入 "@1.12.0全量 帮我看看登录模块的用例"
  ↓
前端识别@提及 → 调用 API GET /legacy/cases/{file_id}/prompt
  ↓
后端渲染Excel内容为文本（最多40000字符）
  ↓
注入到QueryAgent的system prompt（ref_text参数）
  ↓
LLM看到完整的用例内容并回答
```

**优点**：
- ✅ 用户可以精确控制哪些文件被参考
- ✅ 支持历史用例和历史XMind
- ✅ 内容直接注入prompt，LLM可以看到完整信息
- ✅ 长度限制较宽松（40000字符）

**缺点**：
- ❌ **需要手动@提及**：不会自动检索相关历史用例
- ❌ **不参与RAG检索**：@提及的内容不会进入向量检索，只是静态注入
- ❌ **超大文件仍可能截断**：虽然40000字符较大，但极端情况仍会截断

### 2.3 能否作为AI编写用例和XMind时的风格参考？

#### ✅ **已实现，通过Few-shot机制**

**实现方式**：

1. **Feature Flag控制**
   ```json
   // memory/_global/features.json
   {
     "enable_legacy_style_reference": true  // 开启历史风格参考
   }
   ```

2. **同模块匹配逻辑**
   ```python
   # backend/agents/case_gen/pipeline.py:450-524
   def _build_few_shot_by_fp(project, fps):
       """聚合 few-shot 示例：feedback up-voted + legacy 历史用例"""
       
       for fp in fps:  # 遍历每个FeaturePoint
           examples = []
           
           # 第一优先级：反馈点赞的用例
           if use_feedback:
               snaps = feedback_service.select_positive_examples(
                   project, module=fp.module, limit=3
               )
               examples.extend(snaps)
           
           # 第二优先级：同模块/子项的历史用例
           if use_legacy and len(examples) < 3:
               legacy_cases = legacy_service.select_legacy_few_shot(
                   project,
                   module=fp.module,        # 匹配模块
                   sub_item_base=fp.name,   # 匹配子项
                   stage=None,
                   limit=3 - len(examples)
               )
               examples.extend(legacy_cases)
           
           if examples:
               out[fp.fp_id] = examples[:3]  # 最多3条
   ```

3. **多级匹配策略**
   ```python
   # backend/services/legacy_service.py:464-517
   def select_legacy_few_shot(project, module, sub_item_base, stage, limit):
       """按 (module, sub_item_base, stage) 在历史用例里挑相似样例。
       
       匹配优先级：
         1. module + sub_item_base + stage 全等
         2. module + sub_item_base
         3. module
         4. 任意（兜底）
       """
       for level in (1, 2, 3, 4):
           bucket = [c for c in pool if _match(level, c)]
           if bucket:
               selected = bucket[:limit]
               break
   ```

4. **风格画像约束**
   ```python
   # backend/agents/case_gen/pipeline.py:527-565
   def _build_style_hint(project):
       """从 style_profile.json 构造风格约束 prompt"""
       prof = legacy_store.load_style_profile(project)
       
       lines = []
       if cs.avg_steps_per_case > 0:
           lines.append(f"- 步骤数：贴近团队均值 {cs.avg_steps_per_case:.1f} 步/用例")
       if cs.title_scenario_expected_ratio >= 0.5:
           lines.append("- 标题：优先采用「场景-预期结果」格式")
       if cs.common_action_verbs:
           verbs = "、".join(cs.common_action_verbs[:8])
           lines.append(f"- 步骤动词：优先选用 {verbs}")
       
       return "\n".join(lines)
   ```

5. **注入到Generator的System Prompt**
   ```python
   # backend/agents/case_gen/generator.py (伪代码)
   system_prompt = f"""
   你是测试用例生成助手。
   
   {style_hint}  ← 风格约束
   
   Few-shot示例：
   {few_shot_examples}  ← 同模块历史用例
   
   请根据以上风格和示例生成用例。
   """
   ```

**工作流程**：
```
用户请求："为登录模块生成测试用例"
  ↓
Step1 Slicer → 提取FeaturePoint: FP_登录_001
  ↓
Step2 Generator准备生成
  ↓
_build_few_shot_by_fp() 查询同模块历史用例
  ↓
找到3条"登录-账号"相关的历史用例（四级匹配策略）
  ↓
_build_style_hint() 读取风格画像
  ↓
注入到Generator的system prompt
  ↓
LLM看到：
  - 风格约束（步骤数、动词、标题格式）
  - 3条同模块历史用例作为示例
  ↓
生成的用例符合团队风格 ✅
```

**优点**：
- ✅ **自动化**：无需手动选择，自动匹配同模块用例
- ✅ **多维度**：既有few-shot示例，又有风格约束
- ✅ **智能匹配**：按module/sub_item/stage四级匹配策略
- ✅ **优先级合理**：feedback点赞 > 历史用例

**缺点**：
- ⚠️ **需要开启Flag**：默认关闭，需要在设置中手动开启
- ⚠️ **依赖五阶段分析**：风格画像需要先运行五阶段分析生成
- ⚠️ **匹配可能不精确**：如果FP的name和sub_item不完全一致，可能匹配不到

## ❌ 三、平台存在的主要问题

### 问题1：历史用例不会自动进入Memory

**现状**：
- 历史用例存储在 `memory/<project>/legacy/cases/`
- 不会自动同步到 `memory.md` 或 `knowledge_points.jsonl`
- 必须运行五阶段分析才能产生反哺候选

**影响**：
- ❌ 用户上传历史用例后，AI对话时无法自动参考
- ❌ 必须手动@提及或运行五阶段分析
- ❌ 五阶段分析耗时长且产生API费用

**建议方案**：
```python
# 方案A：上传时自动提取关键信息
def ingest_excel_auto_index(project, file):
    cases = parse_excel(file)
    
    # 自动提取高频模块、常见步骤模式
    modules = extract_modules(cases)
    patterns = extract_step_patterns(cases)
    
    # 写入轻量级索引
    save_legacy_index(project, {
        "modules": modules,
        "patterns": patterns,
        "case_count": len(cases)
    })
    
    # 可选：自动注入到memory.md（不经过五阶段分析）
    append_to_memory_md(project, f"""
    ## 历史用例参考：{file.name}
    - 模块分布：{modules}
    - 典型步骤模式：{patterns}
    """)
```

### 问题2：@提及不参与检索

**现状**：
- @提及的内容是静态注入，不参与向量检索
- 虽然有40000字符限制，但仍是硬截断

**影响**：
- ❌ 用户需要知道哪个文件包含所需信息
- ❌ 无法跨多个文件综合参考
- ❌ 超大文件会被截断

**建议方案**：
```python
# 方案B：@提及触发智能检索
def resolve_mention_with_retrieval(project, file_id, query):
    """@提及时不仅注入原文，还检索相关内容"""
    
    # 1. 注入文件元信息（简短）
    meta = get_file_meta(project, file_id)
    ref_text = f"@{meta.name} ({meta.case_count}条用例)"
    
    # 2. 基于query在该文件中检索最相关的用例
    cases = load_cases(project, file_id)
    relevant = semantic_search(query, cases, top_k=5)
    
    # 3. 注入相关用例的完整内容
    for case in relevant:
        ref_text += f"\n\n{render_case_full(case)}"
    
    return ref_text
```

### 问题3：Few-shot匹配不够智能

**现状**：
- 虽然有四级匹配策略，但仍严格按module/sub_item_base匹配
- 不支持语义相似度

**影响**：
- ❌ "登录-账号"和"登录-账户"无法匹配
- ❌ 同义词、近义词无法识别
- ❌ 跨模块的相似模式无法复用

**建议方案**：
```python
# 方案C：语义相似度匹配
def select_legacy_few_shot_semantic(project, fp, limit=3):
    """基于语义相似度选择few-shot"""
    
    # 1. 将FP编码为向量
    fp_embedding = embed(f"{fp.module} {fp.name} {fp.description}")
    
    # 2. 检索所有历史用例的向量表示
    all_cases = load_all_legacy_cases(project)
    case_embeddings = [embed(c.module + c.sub_item + c.title) for c in all_cases]
    
    # 3. 计算相似度并排序
    similarities = cosine_similarity(fp_embedding, case_embeddings)
    top_indices = np.argsort(similarities)[-limit:]
    
    return [all_cases[i] for i in top_indices]
```

### 问题4：风格画像更新不及时

**现状**：
- 风格画像只在五阶段分析完成后更新
- 上传新用例后不会自动更新画像

**影响**：
- ❌ 新上传的用例风格不会被纳入参考
- ❌ 需要重新运行五阶段分析才能更新
- ❌ 耗时且浪费API费用

**建议方案**：
```python
# 方案D：增量更新风格画像
def update_style_profile_incremental(project, new_cases):
    """上传新用例时增量更新风格画像"""
    
    # 加载现有画像
    profile = load_style_profile(project)
    
    # 增量统计
    profile.case_style.total_cases += len(new_cases)
    profile.case_style.avg_steps_per_case = weighted_average(
        profile.case_style.avg_steps_per_case,
        avg_steps(new_cases),
        profile.case_style.total_cases - len(new_cases),
        len(new_cases)
    )
    
    # 更新动词分布
    for case in new_cases:
        for step in case.steps:
            verb = extract_first_verb(step.action)
            profile.case_style.common_action_verbs[verb] += 1
    
    save_style_profile(project, profile)
```

### 问题5：缺少用例质量评估机制

**现状**：
- 历史用例原样作为few-shot
- 没有质量筛选机制

**影响**：
- ❌ 低质量用例会污染生成结果
- ❌ 过时用例可能包含错误信息
- ❌ 无法区分优质用例和普通用例

**建议方案**：
```python
# 方案E：用例质量评分
def score_case_quality(case):
    """评估用例质量"""
    score = 0
    
    # 1. 完整性（是否有前置条件、步骤、预期）
    if case.preconditions: score += 10
    if len(case.steps) >= 3: score += 20
    if all(s.expected for s in case.steps): score += 20
    
    # 2. 规范性（标题格式、动词使用）
    if is_scenario_expected_format(case.title): score += 15
    if uses_standard_verbs(case.steps): score += 15
    
    # 3. 反馈评分（如果有）
    if case.feedback_upvotes: score += case.feedback_upvotes * 10
    
    return score

def select_high_quality_few_shot(project, fp, limit=3):
    """只选择高质量用例作为few-shot"""
    candidates = select_legacy_few_shot(project, fp, limit=limit*3)
    scored = [(c, score_case_quality(c)) for c in candidates]
    scored.sort(key=lambda x: -x[1])
    return [c for c, _ in scored[:limit]]
```

### 问题6：XMind的结构信息利用不足

**现状**：
- XMind被展平为节点列表（保留depth和indent）
- 树形结构的层次关系未被充分利用

**影响**：
- ❌ 无法识别父子节点的依赖关系
- ❌ 无法提取分支覆盖模式
- ❌ 生成XMind时缺乏结构参考

**建议方案**：
```python
# 方案F：保留XMind树结构信息
def extract_xmind_patterns(tree):
    """提取XMind的结构模式"""
    patterns = {
        "max_depth": tree.max_depth(),
        "avg_children": tree.avg_children_per_node(),
        "common_branches": find_common_branch_patterns(tree),
        "leaf_distribution": count_leaves_by_depth(tree)
    }
    return patterns

def inject_xmind_structure_hint(generator, tree):
    """注入XMind结构提示"""
    patterns = extract_xmind_patterns(tree)
    
    hint = f"""
    XMind结构参考：
    - 最大深度：{patterns['max_depth']}层
    - 平均每节点子节点数：{patterns['avg_children']:.1f}
    - 常见分支模式：{patterns['common_branches']}
    
    生成时请保持类似的结构特征。
    """
    
    generator.add_system_hint(hint)
```

### 问题7：缺少版本管理和变更追踪

**现状**：

**建议方案**：
```python
# 方案G：用例版本管理
class CaseVersion:
    file_id: str
    version: int
    timestamp: str
    changes: dict  # 新增/删除/修改的用例ID列表
    diff_summary: str

def track_case_file_changes(project, file_id, old_cases, new_cases):
    """追踪用例文件的变更"""
    old_ids = {c.case_id for c in old_cases}
    new_ids = {c.case_id for c in new_cases}
    
    version = CaseVersion(
        file_id=file_id,
        version=get_next_version(file_id),
        timestamp=utc_iso_z(),
        changes={
            "added": list(new_ids - old_ids),
            "removed": list(old_ids - new_ids),
            "modified": find_modified_cases(old_cases, new_cases)
        }
    )
    
    save_version(project, version)
```
